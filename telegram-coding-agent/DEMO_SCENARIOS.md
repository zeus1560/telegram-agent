# 데모 시나리오 스크립트 (면접 발표용)

**발표 시간:** 5~10분  
**형식:** 라이브 데모 or 영상

---

## 발표 오프닝 (30초)

> "저는 텔레그램으로 원격에서 로컬 코드를 수정하는 AI 코딩 에이전트를 만들었습니다.
> 단순히 AI API를 붙인 게 아니라, 실제로 쓸 수 있는 수준을 목표로 —
> 보안, 동시성 제어, LLM hallucination 방지, 사용자 승인 흐름까지 직접 설계하고 구현했습니다."

---

## 시나리오 1 — 핵심 플로우 (3분)

> **전달 목표:** "AI가 알아서 다 하는 게 아니라, 사람이 최종 승인권을 갖는 구조"

**① 터미널에서 봇 실행 (사전 실행 권장)**
```powershell
node index.js
```
```
🤖 Telegram Coding Agent 시작됨
   타겟 프로젝트: C:\church-platform-main\church-platform-main
```

**② 텔레그램 메시지 전송**
```
api/package.json 파일의 description을 "Church Platform API Server"로 변경해줘
```

**③ 봇 응답 흐름 설명하며 대기**
```
🔍 명령을 분석 중입니다...   ← AI 1단계: 어떤 파일인지 파악
✏️ 수정 코드를 생성 중입니다...  ← AI 2단계: 실제 파일 내용 읽고 수정안 생성
```

> 멘트: "AI 호출을 두 단계로 나눴습니다. 파일 식별은 경량 모델(8b)로 빠르게,
> 실제 코드 수정은 고성능 모델(70b)로 정확하게 — 비용과 속도를 모두 잡기 위한 설계입니다."

**④ Diff + 버튼 수신**
```
📋 수정 계획

📄 api/package.json
```diff
- "description": "Church Platform",
+ "description": "Church Platform API Server",
```
진행할까요?
[✅ 승인]  [❌ 거절]
```

> 멘트: "AI가 임의로 수정하지 않습니다. 반드시 Diff를 보고 사람이 승인해야 파일이 바뀝니다.
> 이 구조를 의도적으로 선택했습니다 — AI를 믿어도, 마지막 판단은 개발자가 합니다."

**⑤ [✅ 승인] 클릭 → 결과 확인**
```
💾 파일 저장 완료. Hot-reload가 서버를 재시작합니다.
✅ 커밋 완료
`feat: api/package.json description 수정`
```

> 멘트: "파일 저장과 Git 커밋이 자동으로 실행됩니다.
> 봇이 서버를 직접 재시작하지 않고 nodemon에 위임한 이유는 — 관리 포인트를 최소화하기 위해서입니다.
> 이미 있는 인프라를 그대로 활용했습니다."

## 시나리오 2 — AI 안전장치 (1분 30초)

> **전달 목표:** "AI가 모르면 추측하지 않고 되묻는다"

**① 모호한 명령 전송**
```
버그 고쳐줘
```

**② 봇 역질문 수신**
```
🤔 어떤 파일의 어떤 버그를 수정할까요?
구체적인 파일명과 수정 내용을 알려주시면 처리하겠습니다.
```

> 멘트: "어떤 파일인지, 무엇을 고칠지 특정할 수 없으면 AI가 추측해서 진행하지 않습니다.
> clarification_needed 상태로 되물어 의도를 좁히는 구조입니다.
> 잘못된 수정이 들어가는 것보다 한 번 더 확인하는 게 낫다고 판단했습니다."

**③ 구체적 명령으로 재입력 → 시나리오 1과 동일하게 진행**
```
api/package.json 파일의 author를 "KNU Church Platform Team"으로 변경해줘
```

```

**② 즉시 두 번째 명령 전송**
```

```

**③ 두 번째 명령에 차단 메시지**
```
현재 이전 지시사항을 처리 중입니다. 완료 후 다시 명령해주세요 ⏳
```

> 멘트: "인메모리 Lock으로 동시 명령을 차단합니다.
> 두 AI 호출이 같은 파일을 동시에 수정하면 충돌이 납니다.
> Redis 같은 외부 저장소 없이 단순하게 구현했고, 봇 재시작 시 자동 해제됩니다.
> 1인 사용자 환경에서 이게 최선의 트레이드오프라고 판단했습니다."

**④ /status 로 상태 확인**
```

```
```

```

## 예상 질문 & 답변

---

**Q. PRD에는 Claude API라고 했는데 실제로는 Groq을 쓰셨네요?**

A. 네, 의도적인 변경입니다. 설계 단계에서 Claude를 명시했지만 구현하면서 두 가지 이유로 Groq으로 바꿨습니다.
첫째, 프로토타입 단계에서 Groq의 무료 티어와 빠른 추론 속도가 반복 테스트에 훨씬 유리했습니다.
둘째, `aiShim.js`가 LLM 프로바이더를 추상화하고 있어서 교체 비용이 낮습니다.
실제로 Claude로 전환하려면 SDK import와 `callGroq` 함수 내부 2곳만 바꾸면 됩니다.
스펙을 못 지킨 게 아니라, 더 실용적인 선택을 한 겁니다.

---

**Q. 테스트 코드가 없는데요?**

A. 맞습니다. 이번 구현에서 의도적으로 빠졌습니다.
현재 aiShim.js가 외부 API에 강하게 의존하고 있어서, 의미 있는 단위 테스트를 작성하려면 Groq API mocking 레이어가 먼저 필요합니다. 시간 제약 상 기능 완성을 우선했지만, 실무라면 `callGroq`를 주입 가능한 의존성으로 분리하고 mock 기반 테스트를 먼저 작성했을 겁니다.

---

**Q. 멀티유저 지원은 안 되나요?**

A. 현재는 1인 전용으로 설계했습니다.
멀티유저를 지원하려면 Lock을 사용자별로 분리하고, pendingChanges를 Map으로 관리하면 됩니다. 지금 구조에서 크게 바꿀 필요 없이 확장 가능합니다. 다만 현재 요구사항이 1인 매니저용이라 over-engineering을 피했습니다.

---

**Q. 파일을 잘못 수정하면 어떻게 복구하나요?**

A. 승인 전에는 [❌ 거절]로 막을 수 있습니다.
승인 후에는 자동 Git 커밋이 됐기 때문에 `git revert`로 되돌릴 수 있습니다. 커밋 메시지는 AI가 의미 있게 생성하므로 히스토리 추적도 됩니다. 봇 자체에 rollback 기능을 넣지 않은 이유는 Git이 이미 그 역할을 하기 때문입니다.

---

**Q. 실서비스에 쓰려면 뭘 더 해야 하나요?**

A. 크게 세 가지입니다.
첫째, 테스트 코드 — AI 응답 mocking 기반의 단위 테스트.
둘째, 로깅 — 현재 console.error 수준인데, Winston 같은 구조화된 로거로 교체하면 운영 중 문제 추적이 쉬워집니다.
셋째, 프로세스 관리 — 현재 `node index.js`로 직접 실행하는데, PM2나 systemd로 데몬화하면 봇이 죽어도 자동 재시작됩니다.
